# EVO 的产品设计：评测之后，团队要做什么

[返回项目首页](../README.md) · [运行与接入](local-setup.md)

## 项目背景

EVO 来自我做 UniHR 和 Clinical Agent 时遇到的问题。演示中的任务可以顺利完成，继续使用时却可能漏掉字段、沿用旧信息，或者给出缺少依据的回答。每次修改之后，如果没有保存原来的问题、预期结果和版本，就很难说清究竟修好了什么。

我希望团队发现一条有问题的回答后，能够说明哪里不对、预期是什么，再安排修复和复测。

## 用户与场景

产品负责人关心先修什么、哪个版本值得继续验证；业务审核者熟悉实际工作，但不一定看得懂执行日志；开发者则需要知道问题在什么条件下发生，怎样重新测出来。因此，这几类使用者都需要方便地查看同一条问题和原始记录。

最初聚焦已有问答和多轮对话 Agent 的小团队：产品正在反复调整提示词、模型、检索或工具调用，已有一些反馈，却缺少一致的验收过程。这个定位来自自身项目实践；是否适合更多团队，还需要真实用户使用后验证。

## 核心动作

### 1. 已有回答也可以先评

团队可能已经积累了一些回答，而接入应用还需要研发配合。我因此保留了“评估已有回答”和“用测试集运行 Agent”两个入口。有历史记录时可以先开始审核，接好应用后再反复运行同一组题。两种方式都会保存问题、回答、参考材料和评审理由。

还没有题库时，可以先描述产品给谁用、要完成什么任务、有哪些限制。AI 先起草少量问题，由人审核，再补充遗漏的场景。题目和预期结果确认后保存为一个版本，后续按同一套标准测试。

### 2. 题目需要明确预期

“回答更好”很难验收；“用户更正时间后，后续安排采用新时间”可以检查。题库记录希望做到什么、依据是什么、有没有多轮条件，而不只存一串提问。

AI 可以检查重复题、覆盖缺口和预期冲突，但不能替业务人员决定正确答案。没有足够事实依据的题目会保留缺口，等待补充。

### 3. 评完以后还能跟进问题

审核者打开结果页，应当能找到有问题的记录，看清哪项要求没有满足、评审根据是什么，以及是否已经有人确认。判断不准确时可以修正，相似的问题可以合并讨论，不同原因也可以分别处理；这些修改都会留下记录。

确认问题后，可以安排改进，并选出后续要重新测试的题目。比较版本时，同时核对题目和评审规则；测试条件不同的结果分开展示，不能直接据此说某个版本更好。

### 4. Agent 可以留在原来的环境里

很多 Agent 在内网或个人开发环境。连接器主动领取任务，在业务系统所在环境调用入口，再上传结果；也支持下载问题包、离线执行后导入。这样，开始评测不必先迁移整个应用。

平台保存执行材料，但不会因此自动获得完整的内部过程。未上报工具步骤时，只能讨论已获得的回答与证据，不能反推某个工具一定出错。

## 这些能力具体用在哪里

| 产品判断 | 采用的能力 | 避免的代价 |
| --- | --- | --- |
| 用户需要尽快开始准备有效问题 | 大模型起草场景，独立检查，再人工确认 | 为了凑题量生成大量无代表性的测试 |
| 审核者需要看懂评审理由 | 评审时一起展示原始引文和验收要求 | 只给总分，无法讨论哪里有问题 |
| 产品负责人需要比较改动 | 固定题目、保留版本和评审口径 | 两次条件不同，却误以为效果提升 |
| 研发需要可靠的复现材料 | 会话记录、版本标识、可选执行步骤与回归题 | 只收到“效果不好”，不知道如何排查 |

## 如何判断这个产品自身是否有用

下一轮试用，我想观察用户能否自己准备一套有效的测试题，看懂并确认或修正评审结果，再在修复后完成一次版本对照。除了记录完成率和所需时间，也要看他们在哪些步骤卡住、对哪些判断有分歧，以及生成的题目有多少实际用不上。

这些使用指标还没有实际结果。目前的自动化测试用于检查软件行为，业务验收需要另外开展。

## 当前边界

当前重点是问答和多轮 Agent，主要模型服务为百炼。Dify、LangChain、LangGraph 提供接入样例，不承诺覆盖所有应用形态。平台不根据一个总分自动批准发布，也不自动修改线上业务系统。

Clinical 示例用于观察信息更正、证据引用等行为，材料是合成测试数据；实际医疗使用仍需独立的专业验证。
