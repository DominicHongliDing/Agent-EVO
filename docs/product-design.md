# EVO 的产品设计：评测之后，团队要做什么

[返回项目首页](../README.md) · [运行与接入](local-setup.md)

## 项目背景

EVO 来自我做 UniHR 和 Clinical Agent 时的实际困惑。演示通常只呈现一条顺利的路径；进入连续任务以后，遗漏字段、沿用旧信息、缺少依据等问题才会显现。修复这类问题时，如果没有保存问题、预期和版本，下一次改动又会回到凭印象判断的状态。

因此，这个项目要解决的核心问题是：团队怎样把零散的“这条回答不太对”，整理成可以讨论、可以安排修复、可以再次验收的工作。

## 用户与场景

产品负责人需要判断先修什么、哪个版本值得继续验证。业务审核者了解场景，但不一定能读执行日志。开发者需要足够具体的失败条件和复测材料。这三类角色应该围绕同一条记录工作。

最初聚焦已有问答和多轮对话 Agent 的小团队：产品正在反复调整提示词、模型、检索或工具调用，已有一些反馈，却缺少一致的验收过程。这个定位来自自身项目实践；是否适合更多团队，还需要真实用户使用后验证。

## 核心动作

### 1. 用两种入口降低开始评测的成本

团队往往已经有历史回答，但应用接入需要研发配合。因此保留“评估已有回答”和“用测试集运行 Agent”两种入口。前者先把审核做起来，后者再建立可重复执行的对照。两种入口都保留问题、回答、参考材料和判断依据。

没有题库的用户可以先描述产品服务对象、任务和限制。AI 起草少量问题供审核，再按场景补齐覆盖。题目和预期经过人工确认后冻结，避免边测边改标准。

### 2. 将业务要求写成可核对的行为

“回答更好”很难验收；“用户更正时间后，后续安排采用新时间”可以检查。题库记录希望做到什么、依据是什么、有没有多轮条件，而不只存一串提问。

AI 可以检查重复题、覆盖缺口和预期冲突，但不能替业务人员决定正确答案。没有足够事实依据的题目会保留缺口，等待补充。

### 3. 将评审结果接到问题处理

结果页应让审核者看清：哪条记录有问题、违反了什么要求、依据在哪里，以及这个判断是否已被人确认。支持修正判决、归组相似问题、拆分不同原因，并保留变更记录。

确认后的问题可以形成改进项和回归候选。版本比较使用对应题目、版本与评审规则；不同条件的结果保持独立，避免把不具可比性的记录解释为提升。

### 4. 让接入方式服从业务环境

很多 Agent 在内网或个人开发环境。连接器主动领取任务，在业务系统所在环境调用入口，再上传结果；也支持下载问题包、离线执行后导入。这样，开始评测不必先迁移整个应用。

平台保存执行材料，但不会因此自动获得完整的内部过程。未上报工具步骤时，只能讨论已获得的回答与证据，不能反推某个工具一定出错。

## 从“模型能做什么”回到“用户需要什么”

| 产品判断 | 采用的能力 | 避免的代价 |
| --- | --- | --- |
| 用户需要尽快开始准备有效问题 | 大模型起草场景，独立检查，再人工确认 | 为了凑题量生成大量无代表性的测试 |
| 审核者需要理解判决理由 | 语义评审关联原始引文和验收要求 | 只给总分，无法讨论哪里有问题 |
| 产品负责人需要比较改动 | 固定题目、保留版本和评审口径 | 两次条件不同，却误以为效果提升 |
| 研发需要可靠的复现材料 | 会话记录、版本标识、可选执行步骤与回归题 | 只收到“效果不好”，不知道如何排查 |

## 如何判断这个产品自身是否有用

下一轮用户验证会围绕三个任务：第一次使用能否准备有效题库；审核者能否根据证据确认或修正一条问题；修复后能否独立完成一次对照。可观察完成率、卡住的步骤、准备时间、评审分歧和无效题比例。

这些是待验证的产品指标，尚不是已经取得的使用成果。当前自动化测试验证的是软件行为，不能代替真实业务验收。

## 当前边界

当前重点是问答和多轮 Agent，主要模型服务为百炼。Dify、LangChain、LangGraph 提供接入样例，不承诺覆盖所有应用形态。平台不根据一个总分自动批准发布，也不自动修改线上业务系统。

Clinical 示例用于观察信息更正、证据引用等行为，材料是合成测试数据；实际医疗使用仍需独立的专业验证。
