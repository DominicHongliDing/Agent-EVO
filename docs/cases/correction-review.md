# 核心案例：回答审核与修复验证

产品负责人、业务审核者和开发者需要对同一条问题形成明确的判断。本例使用 Clinical 的历史测试，说明 EVO 如何组织原文、评审意见与执行依据，再留下修复后的测试要求。

案例材料为虚构病例的实际失败记录，尚无修复后按相同条件重测的结果。

## 先确认问题是什么

用户先说睡眠不好持续“两周”，随后改为“三天”，要求按新时间总结。Agent 再次返回“信息不足，请补充症状、病程”等通用提示，没有完成摘要。

据此可确认的问题是“未按更正后的信息完成总结”。实际回答没有写出具体病程，审核意见应准确反映这一点。相应要求是采用三天、概括已知睡眠信息、单列未知项。

## 一次审核需要留下什么

审核者导入两轮原话、实际回答和来源记录，补充本轮应完成的任务、参考材料及运行条件。AI 可以定位相关片段，草拟未满足的要求、对应引文和可能原因；业务人员对照原文确认或修正意见。

页面需要让原话、要求、回答和理由能够互相对照。已观察的问题与可能原因分开显示；确认的问题保存为待改事项，并附上后续测试输入和判断标准。缺少专业参考时，医学结论保持“无法判断”，本例只评价信息使用与任务完成。

## 从步骤查看到原始记录

| 层次 | 展示内容 | 用途 |
| --- | --- | --- |
| 默认过程 | 中文动作、结果摘要与状态 | 审核者先了解做了什么 |
| 步骤详情 | 输入、输出、工具与异常 | 核对该步骤拿到了什么、交付了什么 |
| 原始记录 | 原事件、参数和返回内容 | 开发者进一步复现与排查 |

三层使用同一条事件依据。无法识别的步骤保留原始说明，业务动作按实际内容确定。

本例记录显示未加载、未使用病例上下文，开发者还需核对请求入口、病例关联与任务识别。平台应分别保存现象和排查假设，方便后续补充依据。

## 修复后怎样重新测试

改进要求是“明确更正后，先完成已知信息总结”。检查是否采用三天、保留睡眠问题、单列未知项，以及是否重复询问已说明的病程。

重新测试保留原始两轮输入与审核标准，记录程序、模型、提示词和本轮提供的病例信息。增加更正含糊、来源冲突、病例切换和后续追问等情况，检查修复是否影响其他任务。

历史记录的程序版本为 `workspace-uncommitted`，尚未对应到确定的提交版本。后续应固定可识别版本，再进行严格的前后对照。

## 分歧与异常处理

| 情况 | 平台应支持的行为 | 谁继续处理 |
| --- | --- | --- |
| 评审声称“仍采用两周”，原文却没有 | 修正为原文支持的问题，保留修改理由 | 产品与业务审核者 |
| 缺前一轮内容 | 标记材料不足，说明哪些部分仍可判断 | 审核者补齐对话 |
| 缺执行步骤 | 先依据回答审核，列出排查所缺材料 | 开发者按需补记录 |
| AI 评审失败 | 保留材料，允许重试或人工审核 | 当前审核者 |
| 没有修复后运行 | 问题保持“待复测” | 开发提交新结果，业务核验 |

## EVO 自身怎样验证

请首次使用者独立完成一次审核：找到两轮原文，从评审意见定位引文，逐层查看处理依据，修正一条不准确的判断，再保存待改事项和测试要求。

记录完成情况、耗时、卡点、需要协助的步骤与误判，并检查材料和状态是否保留。平台已有导入、逐轮审核、处理记录、人工复核与复测任务，这轮用户试用尚待进行。
