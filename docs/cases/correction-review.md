# 一条没有跟上更正的回答，怎样变成可跟进的问题

[返回项目](../../README.md) · [产品设计](../product-design.md) · [打开实际案例](https://dominicspace-agent-showcase.peterzhukejie2020.chatgpt.site/apps/evaluation/index.html?space=history&view=story) · [原文摘录](evidence/clinical-correction.json)

## 先明确这次评测要帮助谁

产品负责人收到“AI 没听懂”的反馈，需要判断改什么；业务审核者需要看到对话，确认究竟哪里不符合要求；开发者则需要原始输入与处理记录，才能复现和排查。

EVO 想让这些人围绕同一条材料讨论。本例采用 Clinical Agent 虚构教学病例的实际历史记录，重点说明评测平台如何组织判断依据、问题和复测要求。

## 从原始对话开始，而不是先看总分

用户先说睡不好持续了“两周”，第二轮更正为“三天”，并要求按新时间总结。Agent 没有完成总结，再次给出了“信息不足，请补充症状、病程”等通用提示。

这不是一条“继续回答两周”的记录。审核意见必须和原文一致：本轮没有使用更正信息交付用户要求的摘要。对应的正确表现可以写成：采用三天，概括已经提供的情况，将未知项单列。

如果只保存一句“上下文能力差”，研发无法知道应该恢复哪条对话，业务也无法确认怎样才算修好。原文、要求和回答需要一起保存。

## 一次审核需要哪些信息

| 环节 | EVO 在这里要支持的工作 |
|---|---|
| 用户输入 | 两轮原话、实际回答，以及来源记录；已有对话可先导入 |
| 审核上下文 | 本轮应完成的任务、最新更正、可用参考材料和运行条件 |
| 处理步骤 | 对照要求审核 → 引用原文 → 人工确认问题 → 保存待改项与复测场景 |
| AI 输出 | 具体未满足的要求、对应引文、仍无法判断的部分；可能原因与已观察问题分开 |
| 用户看到的内容 | 对话、判断理由、处理过程与原始记录；可确认或修正意见，再安排后续验证 |

AI 可以帮助找到相关片段、起草评审理由。事实判断仍取决于提供的材料，业务人员负责确认要求。没有标准答案时，不能让评审模型自行补一个医学结论来评分。

## 为什么时间线分三层

业务审核者首先想知道每一步做了什么、拿到了什么，而不是解读事件名。因此，默认展示中文动作、结果和状态；进入步骤后看输入与结果；最后再展开原始事件和参数。

这三层沿用同一条事件依据。普通人能先理解流程，开发者也能继续核查。对无法识别的步骤保留原始信息，不凭名称推测它完成了某项业务工作。

本例中，查看处理记录可以找到病例上下文未加载、未使用等线索。线索有助于确定排查方向，但不足以证明完整原因：还要检查这条对话通过什么入口发起、病例是否绑定、任务是否被正确识别。

## 确认问题后，怎样安排下一步

适合保存的改进项是“明确更正后，先完成已知信息总结”。其验收条件包括采用三天、保留睡眠问题、未知项单列，以及不重复已经解决的病程问题。

复测应保留同样的两轮输入和审核要求，同时记录程序、模型、提示词及上下文配置。若改动了题目或评分标准，需把变化说明白，再决定哪些结果还能比较。本条历史记录的程序版本标识为工作区未提交状态，后续复测应固定可识别版本，不能声称现有材料已经完成严格的版本对照。

还需要加入反例：更正表达含糊时应询问，来源冲突时应保留待确认，切换病例后应隔离信息。只让回答多出现一个“三天”，并不代表问题已经解决。

## 评审有分歧或材料不足时

| 情况 | 平台应支持的行为 | 后续责任 |
|---|---|---|
| 评审说“仍采用两周”，原文却没有 | 审核者修正判断并保留意见 | 产品与业务依据原文确认 |
| 缺少前一轮内容 | 标记上下文材料不足，不作完整判断 | 补齐原始对话 |
| 没有上报处理步骤 | 只评回答，不断言某工具出错 | 开发者按需补充记录 |
| AI 评审调用失败 | 保留材料，提示失败，可重试或人工审核 | 当前审核者继续处理 |
| 没有修复后的运行 | 保持待复测，不标为问题已解决 | 开发修复后提交新记录 |

## 怎样验收 EVO 本身

这个案例不只检查 Clinical，也能检查 EVO：审核者能否找到原始两轮对话，能否从评审意见回到对应引文，能否逐层查看处理依据，能否修正一条不准确的判断，并保存后续复测要求。

当前平台已有回答导入、逐轮审核、处理记录、人工复核和回归任务等能力。下一轮应请首次使用者完成一次“找问题、确认意见、保存复测”的任务，观察卡点、耗时与误判。软件功能已经存在，并不能代替这项使用验证。

## 目前能得出的结论

公开案例保留了原失败对话及处理记录，尚未记录修复后的同条件测试，也没有本轮用户试用结果。它能够说明我怎样定义和核查一个问题，后续还需要验证修复效果与团队使用价值。
