# 核心案例：信息更正失败的审核与复测

本案例展示 EVO 如何组织一次回答审核：对照原始对话确认问题，查看执行依据，再保存修复后的验证要求。

[返回项目](../../README.md) · [产品设计](../product-design.md) · [在线案例](https://dominicspace-agent-showcase.peterzhukejie2020.chatgpt.site/apps/evaluation/index.html?space=history&view=story) · [原文摘录](evidence/clinical-correction.json)

- 使用者：产品负责人、业务审核者与开发者。
- 输入：两轮对话、实际回答、任务要求与执行记录。
- 交付：有原文支持的审核意见、待改项与复测条件。
- 案例状态：采用 Clinical 虚构病例的实际历史失败记录，尚无修复后的同条件复测。

## 确认未满足的要求

用户先说睡眠不好持续“两周”，随后明确更正为“三天”，要求按新时间总结。Agent 再次返回“信息不足，请补充症状、病程”等通用提示，未完成摘要。

可以确认的审核意见是：本轮未使用更正信息交付所要求的总结。实际回答没有给出具体病程，记录支持的失败类型是“未完成更正后的任务”。

相应预期为：采用三天、概括已有睡眠信息、单列未知项。原话、要求与实际回答共同保存，方便业务确认和开发复现。

## 审核流程与页面行为

| 环节 | EVO 支持的工作 |
| --- | --- |
| 用户输入 | 导入两轮原话、实际回答及来源记录 |
| 审核上下文 | 本轮任务、最新更正、参考材料与运行条件 |
| 处理步骤 | 对照要求审核 → 引用原文 → 人工确认 → 保存待改项与回归场景 |
| 模型输出 | 未满足的要求、对应引文、无法判断部分与可能原因 |
| 页面展示 | 对话、理由、步骤与原始记录；确认或修正意见，再安排验证 |

AI 帮助定位片段、起草评审理由，业务人员确认要求与判断。缺少专业参考时，医学结论保持无法判断；本例只评价信息使用与任务完成。

## 处理时间线的三层信息

| 层次 | 展示内容 | 用途 |
| --- | --- | --- |
| 默认过程 | 中文动作、结果摘要与状态 | 审核者先了解做了什么 |
| 步骤详情 | 输入、输出、工具与异常 | 核对该步骤拿到了什么、交付了什么 |
| 原始记录 | 原事件、参数和返回内容 | 开发者进一步复现与排查 |

三层使用同一条事件依据。无法识别的步骤保留原始说明，具体业务动作按内容确定。

本例记录包含病例上下文未加载、未使用等线索。还需核对调用入口、病例绑定与任务识别，才能确认根因；审核中将观察结果与排查假设分别记录。

## 待改项与复测条件

待改项定义为“明确更正后，先完成已知信息总结”。验收包括采用三天、保留睡眠问题、单列未知内容，并避免重复询问已说明的病程。

复测保留原始两轮输入与审核要求，记录程序、模型、提示词及上下文配置。历史记录的程序版本为 `workspace-uncommitted`，后续需固定可识别版本。当前材料仅包含原失败，严格版本对照仍待补齐。

反例覆盖更正含糊、来源冲突与病例切换；增加后续提问，检查信息能否延续。只增加“三天”字样仍需进一步核查任务是否真正完成。

## 分歧与异常处理

| 情况 | 平台应支持的行为 | 接手人 |
| --- | --- | --- |
| 评审声称“仍采用两周”，原文却没有 | 修正为原文支持的问题，保留修改理由 | 产品与业务审核者 |
| 缺前一轮内容 | 标记上下文材料不足，保留判断范围 | 审核者补齐对话 |
| 缺执行步骤 | 基于回答审核，记录排查信息缺口 | 开发者按需补记录 |
| AI 评审失败 | 保留材料，允许重试或人工审核 | 当前审核者 |
| 没有修复后运行 | 问题保持待复测 | 开发提交新结果，业务核验 |

## EVO 自身的验收

让首次使用者独立完成以下任务：找到两轮原文；从意见定位对应引文；逐层查看处理依据；修正一条不准确的评审；保存待改项和复测条件。

记录完成情况、耗时、卡点、需要协助的步骤与误判，再检查材料和状态是否保留。这项用户验证尚待进行；平台已有导入、逐轮审核、处理记录、人工复核与回归任务等功能。
